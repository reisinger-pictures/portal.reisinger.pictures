# Mollie Payments

## Checkout contract

New positive-value, immediate online orders use Mollie's Payments API. The portal creates one payment for a persisted order and redirects the customer to the HTTPS URL returned by Mollie's hosted checkout link. It does not create catalogues, subscriptions, or standalone reusable payment links. The provider is never told a browser-supplied amount.

The invoice snapshot is written before the provider call and is the order evidence: its integer-cent `total_gross`, EUR currency, line items, license conditions, and any withdrawal-consent evidence are copied into a versioned, immutable payment-attempt snapshot. The provider amount is derived from that snapshot using exact cents; it must equal `orders.total_amount`. This project currently records net and gross as the same cents amount with a null tax rate; the Mollie path uses the persisted gross field rather than inferring that semantic from the column name `total_amount`.

The Payments API request contains only the snapshot amount in EUR, a bounded order reference, the server-generated redirect and webhook URLs, one explicitly configured payment method, and minimal non-PII metadata (`order_id`, payment-attempt UUID, amount in cents, and currency). No customer address, email, license lines, or notes are sent to Mollie. The configured method must be one that works without Mollie-required order lines or extra billing data. An unset or unsupported method fails closed. Live availability for an Austrian business and its fees are not inferred by the application.

The Mollie hosted redirect is presentation only. It cannot set an order paid. The authenticated, owner-scoped order endpoint and the Mollie webhook/reconciliation path are the only sources of payment status for the customer UI. `paid` is the sole Mollie state that can transition an immediate order to `paid`, enqueue its invoice through the existing durable claim, and grant download eligibility. `authorized`, `open`, `pending`, failed, canceled, expired, refunded, and charged-back states do not grant access. Invoice, collective delivery-note, signed-quote, and settled-free orders retain their existing non-provider paths.

## Payment attempts and failure boundaries

`mollie_payment_attempts` is append-only in identity and order evidence. Each row belongs to exactly one order and generation and stores a UUID attempt ID, a unique per-attempt Mollie idempotency key, nullable unique Mollie payment ID, mode, credential fingerprint, exact amount/currency snapshot, hosted URL, provider status, and timestamps. The order/generation and Mollie-payment-ID unique indexes are the durable uniqueness boundaries. Existing Stripe IDs and orders are not copied, rewritten, or deleted.

An attempt row is committed before the remote create. Retries with a known Mollie payment reuse its persisted hosted URL; create recovery may resend the same request and key only while Mollie's one-hour cache window and the same credential fingerprint are known to apply. A 409, a credential change, or an unknown create after the one-hour window is ambiguous: do not create a replacement payment. Keep the order pending and expose a retryable support state. The attempt is deliberately never resolved automatically and no UI path creates a replacement: support checks it in the Mollie Dashboard, and a verified payment still settles through the webhook or `mollie:reconcile-payments`. Retries after a verified failed, canceled, or expired payment may use a new generation, with a bounded attempt count. An open, pending, or authorized attempt blocks replacement.

Classic Mollie webhooks contain only an untrusted payment ID. The handler retrieves the payment using the configured server credential and validates payment ID, attempt/order/brand identity, test/live mode, exact gross cents, and EUR currency before changing state. It binds a missing local payment ID only when the fetched payment metadata identifies an existing creating attempt and all snapshot checks pass. Unknown IDs are acknowledged without exposing order data. Transient provider, database, or mail-queue failures return a retryable response. Duplicate/reordered events and the checkout-return race converge through row locks, unique indexes, conditional state transitions, and the durable invoice-mail claim.

The bounded `mollie:reconcile-payments` command retrieves known nonterminal attempts, applies the same identity and state rules as the webhook, and reports ambiguous attempts and duplicate paid attempts. It runs every five minutes with `withoutOverlapping()` and the shared `onOneServer()` scheduler lock. Attempts with no known payment ID and no safe idempotency retry are never retried automatically. If two different Mollie attempts for one order are verified paid, access/mail is granted at most once; the extra payment is logged for urgent operator action and must be refunded in the Mollie Dashboard, then verified and recorded by reconciliation. Refunds and chargebacks revoke download eligibility through the order's existing `refunded` or `disputed` status handling; a later stale `paid` notification must not reopen access.

## Schema decision (V053)

The existing order columns cannot safely represent more than one provider attempt, distinguish an unknown remote create from a completed create, retain a payment ID after a replacement attempt, or enforce provider-ID uniqueness. V053 therefore adds only `mollie_payment_attempts`, rather than repurposing the Stripe PaymentIntent column or widening an order row with a single Mollie ID. It has a restrictive FK to `orders`, a unique `(order_id, generation)` key, unique attempt and idempotency UUIDs, and a unique nullable provider payment ID. Its snapshot is immutable after insert; mutable status/URL/payment-ID/reconciliation timestamps are the only application-managed updates.

There is no backfill: the table is exclusively for newly-created Mollie attempts and all Stripe history stays in the existing order/payment-intent records. The migration's rollback is intentionally empty; dropping an attempt ledger could erase financial reconciliation evidence. Rolling application code back leaves the additive table unused and does not alter invoice, order, or Stripe data.

## Customer UI contract

The cart offers exactly one online option, "Online-Zahlung", which is the default; the invoice option stays role-gated and unchanged. Submitting a payable cart posts the payment method `mollie` and, when the server answers with a `checkout_url`, performs a top-level navigation to it. The browser accepts only an HTTPS URL on `mollie.com` or a `*.mollie.com` host and otherwise refuses to navigate, keeps the cart, and shows a German error — the server performs the same check, so a tampered response cannot redirect the customer.

The cart and its checkout identity survive the redirect: returning without paying resumes the same order and attempt instead of creating a second payment. The return URL is `/checkout/return?order_id=…`; that view polls the owner-scoped `GET /api/orders/{id}/payment-status` with a bounded number of attempts and derives its state only from the server's order/attempt status (`paid`, ambiguous, failed/canceled/expired, still open). The redirect parameters are never evidence: an untouched order that comes back pending is shown as pending, never as paid. Invoice and delivery-note orders are reported through the existing order views, not through this return page.

## Cutover and operations

Stripe is retired for new online payments: there is no parallel operation of the two providers and no provider selector. Existing Stripe rows, the webhook route, the reconciliation command and historical tooling stay only for historical orders and delayed stale provider events; they cannot create a new Stripe PaymentIntent. The owner confirmed that the Stripe flow was never used and that no Stripe payment is open, so no drain of pending Stripe payments is required. Removing the Stripe package, route and scheduled command is a separate cleanup decision after history no longer needs them and is not part of this change.

Before live activation, the owner must confirm Mollie account activation and the supported payment methods for the Austrian business, verify current transaction fees and any account or optional charges, configure separate test/live credentials and the chosen supported method, and perform an authorized Mollie test-mode smoke. The Stripe side needs no drain step; only its historical records stay. The deploy/restart and live cutover require separate authorization. Missing Mollie configuration disables Mollie payment creation; no fallback to Stripe or client-side payment is allowed.

The webhook URL must be externally reachable over HTTPS in the selected environment. Do not IP-allowlist Mollie webhooks. The API key is server-only and test/live keys are selected explicitly; never log a key, request/response body, email, or payment payload. The customer redirect uses `BrandRegistry::frontendUrl()` for the order's persisted brand and an owner-scoped status lookup. It is validated as HTTPS (HTTP is allowed only in local/testing), and the returned Mollie checkout URL is accepted only from the HTTPS Mollie checkout host. The flow is a top-level navigation, not an embedded frame, so it requires no new CSP script, frame, or connect origin.

## Verification boundary

Provider fakes prove the installed SDK request/response contract without real credentials. Backend concurrency is separately exercised on MariaDB, the production engine; SQLite's in-memory transaction behavior is not evidence of row-lock concurrency. Tests must cover all provider states, exact snapshot identity, unknown/forged/reordered events, create ambiguity and idempotency expiry, retry limits, Stripe-history replay, and at-most-once fulfillment.

The browser side is covered in two layers. `frontend/src/ui/__tests__/CheckoutReturnView.test.tsx` drives every return state (paid, failed, ambiguous, unconfirmed, error, missing reference) against a mocked status endpoint, and `ClientCartView.test.tsx` asserts the hosted redirect, the refusal of a foreign checkout host, and that the cart and checkout identity survive a return without payment. `frontend/tests/e2e/client/checkout-return.spec.ts` then exercises the return route against the real backend without any API mock: a missing reference, an unknown order, and another customer's order must all end in an unreadable state, never in `paid`. No card data and no provider credential are involved.

Journeys that must actually create and complete a Mollie payment cannot run on a stack without a Mollie test account: the server refuses to create a payment and answers `503`. They carry `test.skip(!mollieCheckoutConfigured(), …)` from `frontend/tests/e2e/helpers/MollieE2E.ts`, which reads the same `MOLLIE_KEY` / `MOLLIE_PAYMENT_METHOD` the E2E backend uses, so configuring a test account re-enables them without a code change. Those specs are `client/turnstile-checkout.spec.ts`, `client/card-testing-idempotency.spec.ts`, `client/card-testing-quota-denied.spec.ts` and `client/quote-checkout.spec.ts`; each asserts the redirect to the hosted checkout as its terminal step. Completing a payment inside the hosted page is not automated: the invoice, mail and access grant of a paid order are proven by the backend fakes and the return-view tests, not by a browser.
